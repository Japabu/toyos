# Getting kernel logs off the ThinkPad T14 Gen 2

The machine boots (`README.md`, `specs/metal-track-history.md`) and we are nearly
blind on it. This is what the channels cost and which one to build.

## What we are actually short of

The T14 Gen 2 has no 16550, so `uart_present()` latches false and every drain
writes into a function that returns immediately. The screen is the only channel,
and until this document's Phase 2 landed it was lossy at both ends:

- **The ring was consumed, not retained.** `drain_chunk_to_serial` popped bytes
  the on-screen console had not read yet, and `peek_tail` read `len` — what
  serial still owed the host. Measured: `screen_fatal_halt`, a fatal panic in
  steady state on a machine *with* a console, painted **one row**. The idle loop
  had drained everything else milliseconds earlier. On the T14 the same drain
  throws the boot log away instead of sending it, which is the identical bug
  wearing the opposite hardware.
- **One screen was all there was.** 1920x1080 is 67 rows; the boot log measured
  **82 lines / 5.9 KB / 84 display rows** under metal-sim, and the T14 has more
  CPUs, more PCI devices and real ACPI. Every checkpoint painted the newest 67
  rows and the head was unreachable — there is no key to press, because input on
  that machine is the other open bug.

So the owner photographed the final screen and the lines he needed were gone.
Both halves of that are fixed below. What remains missing is a *byte channel*: a
photograph cannot be grepped, diffed, or fed to the test harness.

## The options

### 1. xHCI Debug Capability (DbC) — the primary, subject to one check

The xHC's own debug device: xECP capability ID **10**, register block at
`DCID/DCDB/DCERSTSZ/DCERSTBA/DCERDP/DCCTRL/DCST/DCPORTSC/DCCP/DCDDI1/DCDDI2`
(xHCI 1.2b §7.6, Table 7-16). Programming it makes the *host* controller
enumerate to the other end as a USB device with two bulk endpoints.

What makes it the right answer in principle:

- **It does not need the xHC.** §7.6 p. 490: the interface is "completely
  independent of the xHCI interface… the USBCMD register R/S flag has no effect
  on the operation of the Debug Capability", and §7.6.2.1 says it can be brought
  up before or after the host driver. No DCBAA, no command ring, no scratchpad,
  no MSI-X, no Run/Stop. It needs BAR0 and an xECP walk, so it could come up in
  phase 2 right after ECAM — **before storage**, which is the phase the first
  metal boot actually died in.
- **No interrupts.** §7.6.4.1 sanctions polling `DCST.ER`. Our panic paths can
  use it.
- **Three rings and a 192-byte context.** One event ring behind a 1-entry ERST,
  one bulk-OUT and one bulk-IN transfer ring, `DbCIC` plus two 64-byte endpoint
  contexts, and four UTF-16LE string descriptors. Hardware synthesises every
  other descriptor. Write-only console, reusing `DmaPool`/`Mmio`/`PciDevice` and
  the TRB types already in `kernel/src/drivers/xhci/`: **~400–700 lines**.
- Linux's early implementation is 1233 lines including an IN path, a tty and
  x86 early-console glue; `connojd/xue` is ~1200 lines of portable core.

And the four things that could sink it, in descending order of danger:

1. **A documented Tiger Lake ↔ USB 3.1 host incompatibility.** Microsoft's
   xHCI-DBC setup page records that a debug cable between a USB 3.1 host and an
   **Ice Lake or Tiger Lake** target fails with "The USB device returned an
   invalid USB BOS descriptor", worked around by a registry key *on the host*.
   The T14 Gen 2 Intel is Tiger Lake and a modern Mac is a USB 3.1/3.2 host —
   this is exactly the failing pair, the BOS descriptor is generated by DbC
   hardware so ToyOS cannot fix it, and macOS has no equivalent knob. A Linux
   host is more lenient. **This is the reason the recommendation is gated.**
2. **macOS has no DbC driver and gives no tty.** Linux binds `1d6b:0010/0011`
   via `usb_debug.c` and hands you `/dev/ttyUSBn`; nothing on macOS matches
   `bInterfaceClass 0xDC / SubClass 0x02`. So "every existing tool keeps working
   unchanged" is only true *after* a host-side libusb bridge exists that reads
   endpoint `0x81` and writes the same byte stream the harness's serial reader
   consumes. That bridge is small and it is real work, and it is not optional.
3. **Our own `HCRST` kills it.** §7.6 p. 490: with `DCST.SBR == 0` a Host
   Controller Reset resets the Debug Capability, and `SBR` is read-only —
   the silicon decides. `kernel/src/drivers/xhci/mod.rs` writes HCRST
   unconditionally. Survivable (init DbC after `xhci::init`, and re-init when
   `DCE` reads back zero), but it has to be designed in.
4. **The cable is not a normal cable.** A USB 3 **A-to-A crossover debug cable**
   (VBUS omitted) — a plain A-to-A drive cable is wired straight through and
   carries VBUS between two hosts. On an Apple-silicon MacBook add a SuperSpeed
   C-male-to-A-female adapter; a C-to-A cable presents the wrong Type-C role.
   The port is not selectable: the DbC attaches to the first root port that sees
   an upstream-facing attach and reports which in read-only `DCST[31:24]`. It
   must be a SuperSpeed port — DCPORTSC's speed note rules out LS/FS/HS. On the
   Intel T14 the Type-C ports hang off the *Thunderbolt* xHCI (`8086:9a13`), a
   different controller from the PCH one behind the USB-A ports; use USB-A.

Whether the T14 advertises it: for the **Intel** variant the Intel 500-series
on-package PCH datasheet says outright "The xHCI supports USB Debug port on all
the USB ports", which is the silicon in this laptop. For an **AMD** T14 Gen 2a I
found no vendor statement, only strong circumstantial evidence — Linux's early
driver carries an explicit AMD endpoint-ID path (`XDBC_EPID_OUT 0/1` vs Intel's
`2/3`, with a comment naming AMD machines), and a Framework Ryzen user reports a
working crossover setup. **Not determined from here.** §"The one question" below.

### 2. USB CDC-ACM dongle — the fallback, not the primary

A USB-serial dongle on our own xHCI host stack. Same order of work (~400–600
lines: a device driver with bulk endpoints on top of the enumeration we have),
and it has one large advantage over DbC — macOS ships the driver, so you get
`/dev/cu.usbserial` and every existing tool really does work unchanged, with no
BOS-descriptor risk and a $10 part.

It loses on the thing that matters. It cannot exist before `xhci::init`, which
is **phase 4, after storage** — and the first metal boot died in phase 3, in
`page_cache::init`. Buffering the ring and flushing once the dongle is up covers
a boot that *completes*; it covers neither a panic nor a hang in phases 1–3,
which is the failure we are buying an instrument for. It also cannot debug the
xHCI driver itself. Build it only if DbC fails the gate and no Linux host is
available to be the DbC peer.

### 3. Persistent-RAM log across reboot (ramoops/pstore-style)

Reserve a physical region, write the ring into it, recover it on the next boot.
No cable, no peer machine, no host driver, and it is the **only** option that
survives a triple fault or a hard hang — where DbC is as dead as the screen.
Kernel cost is small: a fixed region, a memcpy on the panic path, a scan and a
dump at boot.

The risk is entirely in the firmware and cannot be settled from here: whether
Lenovo's UEFI scrubs or retrains DRAM across a warm reset, and whether the
region we pick survives firmware's own allocations. That is a one-boot
experiment on the machine (write a magic, reboot, look for it), and until
someone runs it the feature has an unknown probability of being worthless.
Worth doing *when* a hard hang actually shows up; not before.

### 4. On-screen scrollback and timed paging — built, Phase 2

Cheapest thing on the list, no hardware, no decision, and it is the only channel
that exists from the first instruction of `kernel_main`. It is a photograph: not
greppable, capped at the ring, and useless for the harness. It complements a
byte channel rather than competing with one. See "What was built".

### 5. Netconsole over the built-in Ethernet — do not build

The T14's NIC is an Intel I219-LM: a MAC over an MDIO PHY with the CSME/ME
ownership handshake, which is why `e1000e` is one of the larger Linux Ethernet
drivers. Realistically 1500–3000 lines and a week, for a channel that comes up
*after* the net stack — later than everything else on this list — and that needs
gate N (`specs/net-gate-plan.md`) to be trustworthy. It is the most expensive
option and the latest-available one. The only argument for it is that it needs
no cable the owner does not own, which the crossover cable makes moot.

Also considered and rejected outright: **Intel DCI** over USB-C — a different
feature from DbC, needing an `IA32_DEBUG_INTERFACE` MSR, hidden firmware
consent options *and* a PCH soft-strap in the SPI flash descriptor; the best
public write-up needed an FPGA and a SOIC clip on the flash chip, and the host
tooling is Windows/Linux only. **Port 0x80** — eSPI, no LPC header, no slot.
**A hidden board UART** — real pads reportedly exist on the NM-D351 family, but
that is disassembly, soldering and a level shifter, and I have not read a
schematic. **Logging to the internal NVMe** — forbidden, see the hazard below.

## Recommendation

**Primary: xHCI DbC — after the owner runs one 5-minute check.** It is the only
option that is available before storage, independent of our own driver, and
survives a panic, and it turns the T14 into a machine with a serial console
rather than a machine with a camera pointed at it. But two of its four risks
(the Tiger Lake BOS bug, the missing macOS driver) live entirely on the *host*
side, where no amount of kernel work helps, and one Linux live-USB session
settles both before a line of Rust is written. Writing the driver first and
discovering the Mac will not enumerate it is the expensive order.

**Complement: the paged on-screen console — built now.** It needs no hardware
and no decision, it is the only thing that reports a fault before PCI exists,
and it is what a hang leaves behind when DbC has nothing to say because nobody
called it. The two do not overlap.

**Would not build: netconsole** (§5) — most expensive, latest-available, and
gated behind a whole other test gate. **Would not build CDC-ACM** unless DbC
fails the gate (§2) — same cost, strictly later availability, blind to the phase
where the machine actually died.

## The one question the owner has to answer

Boot an Ubuntu live USB on the T14 (`CONFIG_USB_XHCI_DBGCAP=y` since 18.10) with
the crossover cable to the Mac:

```
ls -l /sys/bus/pci/devices/*/dbc          # exists only where the xECP was found
echo enable | sudo tee /sys/bus/pci/devices/<bdf>/dbc
cat /sys/bus/pci/devices/<bdf>/dbc        # disabled -> enabled -> configured
```

Move the cable through each USB-A port. **The port where `dbc` reads
`configured` is the answer to all of it**: that state means the Mac enumerated
and configured the device, which kills the BOS-descriptor question, names the
physical connector, and proves the capability exists on this silicon. If it
sticks at `enabled` and never reaches `configured`, DbC is dead against a Mac —
and still alive against any Linux box or Raspberry Pi as the log host, which is
the cheaper fallback than building CDC-ACM.

Worth capturing in the same session, since it decides whether the DbC console
has to be re-initialised after our own `HCRST`: read `DCCTRL`+4 (`DCST`) bit 1
(`SBR`) by mmapping `resource0` and walking xECP for ID 10.

## What was built (Phase 2)

The framebuffer console is no longer lossy, and neither half needed new hardware
or a decision from the owner.

- **`log_ring` retains what serial has collected.** `tail`/`len` stay serial's
  cursor; a new `retained` counts bytes still readable behind `head` and only a
  64 KiB wrap shortens it. `peek_tail` reads `retained`. Zero new memory.
  `screen_fatal_halt` went from **1 row to 96**.
- **The console paginates.** `paint` takes a `Page`, `pagination` decides the
  page count from the wrapped row count, and a `[page n/m]` footer takes the
  bottom row *only* when there is more than one page — so a report that fits is
  byte-identical to what it was, which is why `screen_early_panic` did not move.
- **`page_forever` cycles the pages on a halted machine**, 3 s each, driven off
  `clock::nanos_since_boot` (an `rdtsc` and two relaxed loads — no lock, no
  MMIO). It runs from `halt_all_cpus` strictly *after* `panic_flush`, and only
  on the CPU whose `render` took `PAINTING`, so it can never cost the serial
  report and no second CPU paints alongside. It spins rather than halting:
  nothing would wake a halted CPU, and re-arming the LAPIC timer would aim an
  interrupt at the scheduler from inside a panic.

The design rules held: nothing on the paint path takes a lock, allocates, or
formats beyond the footer's two integers, and the reentry and early-boot panic
branches deliberately do not page.

`screen_paged_scrollback` is the new gate. It asserts that the report page
*cannot* hold the first line of the boot log — the premise, so the test cannot
pass vacuously — and that the line reaches the screen anyway. Both negatives
were run: disabling `page_forever` fails it on the exact diagnostic, and
`screen_fatal_halt`'s row-count assertion is what fails if `peek_tail` goes back
to reading the drained cursor.

## Follow-ups this turned up

- **`panic_console::capture`/`discard_capture` may now be redundant.** They
  exist because `panic_flush` drained the ring out from under the renderer; a
  drain no longer erases, so the live tail after the flush is the same text.
  Removing them touches the panic handler's most carefully argued ordering, so
  it is a change of its own, not a rider on this one.
- **A live on-screen channel for a *running* machine: considered and declined**
  (2026-08-01), not deferred. It would close `specs/issues/hardware/`'s "no output channel
  once boot is done", and it is still the wrong trade.

  A periodic repainter has to render from timer context through the same
  renderer the panic path uses. That renderer takes **no lock of any kind** —
  which is what makes it safe to arm before `serial::init` and to run from a
  fatal panic under arbitrary held locks. Sharing it with a periodic painter
  means the two interleave, and the failure mode is a garbled final frame:
  corrupting the one diagnostic that exists on metal in order to add a
  convenience channel. That trade is backwards.

  Neither escape survives. A second framebuffer region costs memory and inherits
  the `gpu::set_resolution` hazard already on the books — it frees the old
  framebuffer while consumers may hold pointers into it. A lock the panic path
  is allowed to skip reintroduces exactly the interleave the no-lock rule exists
  to prevent.

  And the coverage is thin. The mute window is `Boot: complete` → the
  compositor's terminal, milliseconds on a healthy boot. Fatal panics already
  paint. The six phase checkpoints already repaint, so a wedge shows the last
  phase reached. What is left uncovered is a machine that is alive, past boot,
  not panicking, and not reaching the compositor — narrow, against a risk taken
  in every case.

  **Reopens if** xHCI DbC (§1) fails its hardware gate, which would leave the
  T14 with no post-boot byte channel at all. DbC is the designed fix and makes
  every existing tool work unchanged; this is only worth its cost if that is
  gone.
- **`MAX_ROWS` is 96 on a 128-row QEMU screen.** With paging the cap costs a
  page boundary rather than lost text, but it is now arbitrary.
